# 棋谱格式适配器状态

PikaDesk 使用 `ManualDocument` 作为四种适配器和主界面文件入口的共同边界：一个已验证的 `GameTree`、明确的对局结果，以及有界、可规范化的标签。文件读写不再路由到旧 PGN/XQF/CBR/TXQ 实现；剪贴板的历史中文棋谱文本仍是独立兼容路径。

| 格式 | 新适配器状态 | 当前可验证范围 | 尚未完成 |
|---|---|---|---|
| PGN | 内核与界面接线通过 | ICCS、UTF-8/GB18030/带 BOM UTF-16、标签、FEN、结果、注释、主线与括号变例 | Chinese/WXF 记谱 |
| XQF | 1.0 内核与界面接线通过 | 公开的 0x0A 格式、GBK、任意合法初始局面、主线、结果、元数据、逐着评注 | 加密高版本；1.0 本身无变例字段 |
| CBR | v2 读取与界面接线通过；导出候选 | 两份真实 CCBridge v2 样例、UTF-16LE 元数据/注释、任意合法初始局面、主线与变例树、结果、内部往返 | 在官方 CCBridge 中黑盒验证导出；v1、CBF/CBL |
| TXQ | 安全内核与旧界面接线通过 | `PDTX 1` 完整树往返；旧 TCHESS Java 序列化只读迁移；结果、元数据、注释、评估与主线 | 尚无独立真实旧 TXQ 样例；新版文件不能由旧 TCHESS 读取 |

## PGN 契约

- 首标签必须是 `[Game "Chinese Chess"]`，着法区不得再出现标签。
- 当前只接受 `Format "ICCS"`。坐标可读 `B0-C2` 或 `b0c2`，保存统一为大写带连字符的 ICCS。
- `Result` 标签和着法区末尾结果必须一致；结果只允许 `1-0`、`0-1`、`1/2-1/2`、`*`。
- 花括号和分号注释进入对应树节点；无法无损表示的 `}` 会在导出前返回 `UNREPRESENTABLE_COMMENT`，不会偷偷改写。
- 圆括号变例进入同一 `GameTree`，首个分支保持主线；空变例、重复变例、括号失配和非法走法均返回带代码与偏移的 `PgnException`。
- 数字 NAG 暂不保存，但每项都产生 `UNSUPPORTED_NAG`；警告达到 1,024 项后停止，防止恶意输入堆积对象。
- 输入和输出各限 4 MiB，最多 50,000 步、256 层变例、64 个标签、16,384 字符注释。输入流只读取上限加一字节；输出在生成过程中持续检查大小。
- 解码优先严格 UTF-8；国内旧文件可严格回退 GB18030，带 BOM 的 UTF-16 也可读取，并产生 `LEGACY_ENCODING`。不使用替换字符掩盖损坏字节。

PGN 的历史公开规范把 Chinese、WXF、ICCS 都列为合法 `Format`；当前明确只实现 ICCS，是因为其与应用内部 UCCI 坐标一一对应，且鲨鱼公开更新说明也把 ICCS 读写列为现有能力。其余两种不会被当作 ICCS 猜测解析。

## XQF 1.0 契约

- `Xqf10Adapter` 只接受公开规格中的版本 `0x0A`：1024 字节头、固定第 0 步和从 `0x0408` 开始的主线记录。后续加密版本返回 `UNSUPPORTED_VERSION`，不会套用未经样例验证的解密公式。
- 头部严格检查 `XQ` 标记、保留区、结果、棋局类型、字符串长度/零填充、32 个棋子坐标和重复占位；棋步严格检查坐标偏移、`00/F0` 延续标志、保留字节、无符号小端评注长度及文件尾。
- 32 个棋子位置会重建合法 FEN，随后每步仍通过 `GameTree` 的完整象棋规则验证。旧实现中的非法坐标钳制、截断后静默结束和异常后返回 `null` 不进入新适配器。
- 标题、赛事、日期、地点、双方棋手、用时规则、双方用时、讲评人和作者按有界 GBK 文本读写；结果和全局/布局/中局/残局类型也保留。损坏字节不使用替换字符掩盖。
- XQF 1.0 的公开规格没有行棋方字段，读取时明确报告 `ASSUMED_RED_TO_MOVE`；黑方先行的文档不能安全导出。格式也明确“不支持变着”，因此含变例的树返回 `UNSUPPORTED_VARIATIONS`，绝不静默拍平。
- 根注释无法放入固定第 0 步而会拒绝导出；引擎评估和未知元数据只有在 `WriteResult` 中产生显式遗漏通知后才允许写出。
- 输入/输出各限 16 MiB，最多 50,000 步，单条评注最多 16,384 个 GBK 字节。输入流只读取上限加一字节；输出先在有界缓冲中完整验证，超限时不向目标流写入半个文件。

## CBR v2 契约

- `Cbr2Adapter` 只接受 `CCBridge Record\0` 且版本字节为 `2` 的单局 CBR。当前布局依据 CCBridge 用户手册的能力说明、社区反向格式实现和两份固定哈希真实样例交叉验证；没有把社区推断写成官方二进制规范。
- 2,214 字节头中的 UTF-16LE 标题、赛事、日期、地点、红方、黑方、结果、行棋方、90 格棋盘和 `ff ff ff ff` 哨兵都经过边界检查。固定字段只在偶数字节边界查找终止符，避免社区解析器把 `Test` 截成 `Tes` 的非对齐双零问题。
- 根注释和逐着注释使用严格 UTF-16LE；记录标志保存主线、兄弟变例和注释。两份真实样例的 SHA-256 分别为 `6897fe17…ea7c64` 与 `7c1e4417…a193`，后者导入为 103 节点并核对首个二分支的准确父子关系。
- 真实文件中记录第二字节同时出现 `0` 与 `1`。当前接受这两个已见值，对 `1` 返回 `UNSUPPORTED_STEP_ATTRIBUTE`，因为其展示语义尚无可信定义；其他值拒绝。引擎评估和未知元数据在导出时也显式报告，不会静默声称无损。
- 输入/输出各限 16 MiB，最多 50,000 步、256 层嵌套变例、单条注释 16,384 字符。非法棋盘、错方/非法走法、重复兄弟着法、截断、超长、奇数字节文本和尾随数据均返回代码与偏移；输出在完整有界缓冲验证后才写目标流。
- 导出端按社区反向布局生成 v2，并已通过 PikaDesk 自身的变例、结果、元数据、注释与黑方先行往返；但尚未取得官方 CCBridge 应用黑盒验证，所以每次写出固定返回 `UNVERIFIED_EXTERNAL_WRITER`。在完成该验证前，不把它描述为已证实的 CCBridge 写入兼容。

## TXQ / PDTX 1 契约

- 旧 TCHESS 的 `.txq` 是以 `AC ED 00 05` 开头的 Java 原生对象流，根对象为 `ChessManual`，棋谱节点为 `ManualRecord`。PikaDesk 仅为迁移旧文件保留只读入口；新保存统一写入以 `PDTX` 开头的版本 1 格式，不再生成 Java 对象流。
- 旧流在读取对象前同时启用精确类名白名单和 Java 21 `ObjectInputFilter`：代理类、额外类、超过 256 层、100,000 引用、50,000 数组元素或 16 MiB 的图一律拒绝。读取后还会重建到 `GameTree`，再检查 FEN、行棋方、走法合法性、重复分支、共享对象/环、主线索引和总节点数。
- 旧格式没有对局结果字段，迁移时结果明确设为“进行中”，并返回 `LEGACY_RESULT_UNAVAILABLE`；旧分数按深度 1、来源 `Legacy TXQ` 的节点评估保存。标题、日期、地点、红黑棋手、根/逐着注释和选择的主线均迁移。
- `PDTX 1` 保存结果、规范化元数据和现有 `PDTR` 棋谱树，因此可往返 UUID、当前位置、主线、变例、注释和评估。元数据与树文本使用严格 UTF-8，损坏字节、重复键、未知版本、尾随数据、截断和超限都以代码及偏移失败。
- 输入、输出各限 16 MiB，总节点限 50,000；输出先在内存有界缓冲中完整验证。旧界面保存时再写同目录临时文件，并优先原子替换，所以校验失败不会先截断已有棋谱。
- 兼容边界必须公开：旧 TCHESS 可以由 PikaDesk 迁移读取，但旧 TCHESS 不认识新版 `PDTX 1`。截至 2026-08-27 未找到独立发布的真实旧 TXQ 样例；测试使用固定提交中具有精确类名和 `serialVersionUID=1` 的 TCHESS 模型生成对象流，证明当前类结构迁移，不声称已完成第三方 TXQ 黑盒兼容。

## 主界面文件网关

- `ManualFileGateway` 依据不区分大小写的 `.txq/.pgn/.xqf/.cbr` 扩展名路由到四个新适配器；打开与另存为筛选项由同一格式枚举生成，避免界面和实际能力漂移。
- 打开成功前不改变当前棋谱；保存先在适配器内完整编码，再写同目录临时文件并原子替换。格式拒绝、校验失败或目录错误时，原文件和当前文件身份均保持不变。
- 对局结果和界面没有输入框的合法元数据会保存在当前会话中。标题、日期、地点和棋手以界面编辑后的值覆盖；`Annotator`、`TimeControl` 等隐藏标签在跨格式保存时保留，或由目标适配器明确返回遗漏提示。
- 导入和导出通知最多在对话框显示前 8 条及剩余计数；例如旧 TXQ 迁移、XQF 红方先行假设、CBR 候选写出状态都会呈现给用户，不再只写终端或静默忽略。
