# 开局库格式与安全批处理基线

状态：XQB v1 批处理内核、JavaFX 用户界面、跨进程断点恢复和三种本地库的安全只读入口已实现；标准 SQLite OBK 可以从用户已有标准 OBK 生成规范化高可信子集，但不创建新局面键；PF 写入与私有/魔改 OBK 的完整兼容仍受公开证据限制。

## 已核实的格式边界

| 名称 | 当前扩展名 | 可核实结构 | 当前结论 |
|---|---|---|---|
| XQB v1 | `.xqb` | SQLite 3；`information(name,value)` 声明 `version=1`、`type=xiangqi`；`book` 含 `id/key/move/score/win/draw/lost/valid/memo` | 有原作者公开说明、建库样例和真实小型样例，可以实现独立互操作 |
| PF | `.pfBook` | TCHESS 查询 `pfBook` 表的 `vkey/vmove/vscore/vwin/vdraw/vlost/vvalid/vmemo`；鹏飞官方只确认其软件可把兵河库转换成鹏飞库，移动版要求先由电脑版转换 | 官方没有公开建表规范或许可清晰样例，且官方说明存在加密商业库；只对标准 SQLite、已知字段的未加密变体作保守只读适配，暂不生成 |
| BH/OBK | `.obk` | 公开兵河技术资料给出 90 格 Zobrist、红方行棋常数、初始局面键、16 位着法和 `bhobk` 查询字段；TCHESS 负键路径沿用浮点位模式匹配 | 鲨鱼官方明确说明真实 OBK 基于无源码的“魔改版 SQLite”、只支持 Win32；标准 SQLite 驱动不能据此宣称完整兼容。PikaDesk 只读取标准容器变体，且只允许由已有标准 OBK 筛选出新的标准 OBK 子集，不反推或新建哈希位置 |

仓库中原有的选择器实际只接受 `.xqb`、`.obk` 和 `.pfBook`。“BH”只是当前适配器类名，不代表另有已证实的 `.bh` 文件格式。兵河资料仓库固定在 `fengyunnc/fy` 的 `f7d72009def464dcb795a3853b23c2f9b55fafa9`；仓库没有许可证，因此只提取互操作事实，不复制 C 代码、常量表或文件内容。

XQB 证据固定在 `fisherfan/xqbook` 的 `93964abe35543e4338c3501618240ac191436d30`。该提交的 `book.xqb` SHA-256 为 `721e547016015b271f922041dfd666a31a68a2c130a2ef87bfd59740d705b16b`，本机只读互操作检查读取 2 行、写出 2 行、零拒绝。该上游提交没有 `LICENSE`、`COPYING` 或 `NOTICE` 文件，因此 PikaDesk 不复制其 C 实现或样例二进制，只依据公开字段和位布局事实编写独立 Java 实现。

## XQB 批处理契约

`XqbBatchService` 接收一到多个 XQB v1 输入，生成一个新的规范化 XQB：

1. 输入必须是普通 `.xqb` 文件、具有 SQLite 3 文件头，并满足文件数与单文件大小上限。
2. 每个输入使用 SQLite `mode=ro`、私有缓存和 JDBC `READONLY` 标志打开；同时关闭扩展加载，启用 `query_only` 与 `trusted_schema=OFF`。
3. 连接限制 SQL 长度、列数、表达式深度、虚拟机操作数、变量、附加数据库、触发器深度、工作线程和缓存规模。
4. 只接受 XQB v1/xiangqi 的必需表、列和 SQLite 类型亲和性；信息表最多读取 16 项。
5. 全批次默认最多 500 万行。局面键最多 128 字节，并验证恰好编码 90 个格子、最多 32 枚棋子、保留编码和尾部填充位。
6. 着法必须是两个不同的 9×10 棋盘坐标；胜/和/负统计必须是非负 32 位整数；`valid` 只能为 0 或 1；备注必须是有界严格 UTF-8。
7. 只删除所有字段完全相同的重复记录。同一局面和着法若统计或备注不同，将全部保留；在没有权威合并语义时不擅自相加、平均或覆盖。
8. 输入先进入带复合主键的独立暂存库，再按 `key/move/score/win/draw/lost/valid/null标记/memo` 规范排序写出。因此输入顺序不同仍得到相同的输出字节。
9. 进度事件分别报告校验、读取、写入和完成阶段；读取与写入逐行检查取消标记。
10. 成功前只操作同目录随机临时文件。取消、坏库、超限或 SQL 错误都会回滚并清理临时文件，已有目标文件不变；成功后才原子替换。

报告保存扫描、写入、精确重复、拒绝总数。坏行样例默认最多保留 200 条，其余只累计数量，避免错误报告本身耗尽内存。

## 已验证行为

`XqbBatchServiceTest` 当前覆盖：

- 两库合并、精确去重、冲突记录保留；
- 输入顺序反转后的 SHA-256 完全一致；
- 表缺失、列类型错误、非 SQLite、超大文件、总行数超限；
- 错误样例上限及省略计数；
- 读取源文件不改写且不产生 journal/WAL/SHM；
- 路径相同或硬链接相同的输入/输出重叠拒绝；
- 读取阶段取消和规范写出阶段取消均保持旧目标并清理临时文件；
- 进度阶段存在且计数单调。

主界面“开局库 → 批量制作 XQB”已接入多选源文件、输出选择、开始、取消、进度、状态和有界校验报告。工作在线程外执行；取消只发出协作式请求，等待内核回滚并清理临时文件后才恢复按钮，避免把“界面任务已取消”误当成“文件工作已经停止”。

`BookBatchViewModelTest` 与 `BookBatchUiContractTest` 覆盖输入去重、就绪状态、安全错误文案、FXML 控件与独立验收入口。可用 `mvnw.cmd --batch-mode javafx:run@book-batch-test` 在不启动棋盘引擎的情况下验收窗口；Windows UI Automation 已核对初始禁用状态、中文可访问名称和应用内关闭流程。

## 断点恢复契约

`XqbResumableBatchService` 在输出文件同目录使用 `.<输出名>.pikadesk-resume` 工作目录。恢复粒度是“一个源文件”：当前源文件被取消或进程中断时会从头重做，但此前已经完成的源文件会直接复用。

1. 初次任务为每个源文件记录规范化绝对路径、大小、修改时间和流式 SHA-256；恢复前、最终合并前后再次复核，任何变化都拒绝使用旧断点。
2. 每个源文件由原有有界内核独立生成规范化 XQB 分片；只有完整关闭并重新计算大小与 SHA-256 后，才优先以同目录原子移动更新恢复清单；平台不支持原子移动时，替换后的清单仍必须通过完整校验才能使用。
3. 清单采用有 1 MiB 上限的严格二进制格式，文本按严格 UTF-8 解码，末尾带 SHA-256 完整性校验；分片也各有独立指纹。校验用于发现损坏，不作为抵抗同一系统账号恶意改写的认证机制。
4. 全批次 500 万行上限和问题样例上限按已完成分片扣减，不能通过拆成多个源文件绕过。
5. 同一输出对应的 `batch.lock` 使用操作系统文件锁；第二个进程不能同时修改该恢复任务。锁文件可能留在空工作目录中，但不包含棋局数据。
6. 最终合并先写工作目录内的候选输出；再次校验全部源文件和分片后才替换用户目标。取消、损坏、超限、源变化和锁冲突都不会覆盖已有输出。
7. 界面重新选择同一输出文件时会载入断点中的源列表并锁定编辑；“清除断点”只删除 PikaDesk 已知的清单与分片，不删除源文件、已有输出或工作目录中的未知文件。

`XqbResumableBatchServiceTest` 已覆盖两次独立服务实例恢复与新建结果逐字节一致、全部分片完成后恢复最终合并、源变化、分片变化、全局行数上限、损坏清单、保守清除以及并发文件锁。JavaFX 离线验收再次确认进度条实际可见、恢复按钮初始状态正确、报告区保留可读高度。

## 本地库安全读取契约

`XqbOpenBook`、`PfOpenBook` 和 `BhOpenBook` 现在共用 `SafeSqliteOpenBookSupport`：

1. 只接受普通文件、匹配扩展名、8 GiB 以内且具有标准 SQLite 3 文件头的容器；加密库、私有容器和魔改 OBK 会以稳定错误码拒绝，不尝试破解或降级为可写打开。
2. 使用 SQLite URI `mode=ro`、私有缓存和 JDBC 只读标志；关闭扩展加载，启用 `query_only`、`trusted_schema=OFF` 和每连接运行时限额。
3. 加载时检查唯一数据表和必需字段类型。XQB 还必须唯一声明 `version=1`、`type=xiangqi`。
4. 所有局面键都使用参数化查询；单个局面最多返回 256 条结果，查询超时 3 秒，备注最多 4096 个 UTF-8 字节。
5. 分数必须是有符号 32 位整数；胜、和、负必须是非负 32 位整数；着法的两个坐标必须都在 9×10 棋盘内且不同。坏行被跳过并记录稳定诊断，零对局统计的胜率为 0。
6. 左右镜像键相同时只查询一次，避免初始局面等对称局面重复显示同一库招。
7. 本地库重新载入失败后，界面以文件名和稳定错误码提示，诊断不包含用户的绝对目录；不再向控制台打印异常堆栈。

`SqliteOpenBookAdapterTest` 使用独立创建的标准 SQLite 契约样例验证 XQB/PF/OBK 读取、源文件 SHA-256 不变且没有 journal/WAL/SHM、坏行跳过、256 条上限、容器/表错误码和路径脱敏。该测试证明 PikaDesk 自己的适配契约，不是对真实加密 PF 或魔改 OBK 的兼容认证。

## 标准 OBK 高可信筛选契约

`ObkQualityFilterService` 只从一个用户已有的标准 SQLite `bhobk` 输入生成子集：

1. 源库使用 `mode=ro`、`immutable=1`、私有缓存、`query_only` 与 `trusted_schema=OFF` 打开；扩展加载关闭，文件、行数、SQL、列、表达式、变量和内存相关上限均显式约束。发现 `-journal`、`-wal` 或 `-shm` 时拒绝把库视为不可变文件，避免忽略尚未合并的数据。
2. 只接受整数键或有限实数键、C90 结构合法着法、有符号 32 位分数、非负胜和负统计、0/1 有效标记以及有界严格 UTF-8 备注。
3. 当前本机精选阈值为 `vvalid=1` 且 `vscore>=3`。阈值来自用户库初始局面与 ChessDB 的交叉核验；它是可复现筛选规则，不是“理论必胜”证明。
4. 同一键和着法只保留一条，按分数、总样本数、胜、和、较少负局、非空备注和稳定源行顺序决胜；统计不相加，避免把未知来源的重复记录虚增为更多实战样本。
5. 输入不改写。输出先写同目录随机临时数据库，通过 SQLite `quick_check` 并完整关闭后才原子替换；取消、坏库、超限或 SQL 失败均保留已有目标并清理临时文件。
6. 输出仍是标准 SQLite OBK，只重写输入中能验证的记录，不声称兼容加密、私有或魔改 OBK，也不可能从不可逆哈希恢复未出现的 FEN。

首启本机配置默认仍只允许 XQB；只有同时设置 `book.allowLegacyObk=true` 才能载入标准 OBK，并会先校验 SQLite 3 文件头。配置文件按 UTF-8 读取，因此本机中文文件名不会再被 Java Properties 的历史 ISO-8859-1 默认编码破坏。

## 尚未声称完成

- PF 还不能由 PikaDesk 批量生成；OBK 只能从用户已有的标准 SQLite OBK 过滤成子集，不能凭棋谱新建键、做无损 OBK→XQB 转换或处理私有/加密变体。
- 标准 SQLite 的 PF/OBK 契约样例通过，不等于真实商业库兼容；在取得合法样例前，不把“表名匹配”写成“完整支持”。
