# PikaDesk 是怎样被做出来的

PikaDesk 的起点，是一个很朴素的愿望：让中国象棋爱好者无需订阅、无需上传棋局，也能在自己的电脑上拥有一套透明、强大、可验证的分析工具。

这不是一次简单的换皮，也不是对商业程序的破解。项目选择从公开源码、标准协议和可复现测试出发，把研究、取舍、实现、失败和验证逐步收束成一个独立、免费、本地优先的桌面工作台。

## 第一阶段：寻找可信的技术基座

调研从引擎、界面、棋谱格式和国内象棋生态同时展开。

- Pikafish 是强大的开源中国象棋引擎，但官方明确说明它本身不包含图形界面；
- TCHESS 已具备 JavaFX 跨平台界面、UCI/UCCI、棋谱、连线和开局库基础；
- 其他开源项目为规则、格式兼容和桌面体验提供了交叉参考；
- 鲨鱼公开帮助与更新记录被用作“用户任务清单”，不作为源码、素材或授权机制来源。

最终确定：固定 TCHESS 提交 `2d41525095639548059ebd930b0af4d29efc1364` 为上游基线，以标准 UCI/UCCI 接入 Pikafish，以 GPL v3 延续开源义务。

## 第二阶段：从上游项目变成独立产品

项目首先完成了 PikaDesk 品牌化：统一 Maven 坐标、窗口标题、关于页面、导出署名和许可证入口，同时保留 TCHESS 的作者、源码链接与许可证归属。

随后建立可复现工程：固定 JDK 21、Maven 3.9.16、Wrapper 校验值、依赖版本和 53 项初始资源哈希。即使开发机没有全局 Maven，也可以从仓库执行测试和构建。

本地优先不是一句口号。上游首次运行默认访问 ChessDB，PikaDesk 将云库和库招默认改为关闭，并通过真实启动观察确认新安装在未授权时不产生网络访问。

## 第三阶段：先建立安全边界，再谈自动化

窗口自动化最危险的地方不是“点不动”，而是“点错了还继续”。因此 PikaDesk 先实现纯状态机安全内核，再接触真实鼠标输入。

完整闭环被拆成：

1. 用户明确选择目标；
2. 校验进程、窗口类、客户区、DPI 和版本；
3. 识别棋盘和完整局面；
4. 验证局面与候选走法合法；
5. 生成一次性事件许可；
6. 每个鼠标事件前复核焦点和用户活动；
7. 输入一着后等待视觉确认；
8. 任何失败、超时、窗口变化或用户输入立即停止。

为了不依赖账号或网络，项目制作了独立本地测试棋盘，可切换红黑方向、主题、缩放和动画速度，并记录真实收到的 UCCI 走法。经典主题红/黑方向与 100%/150% 测试缩放已完成真实端到端验证。

耐久测试最长连续确认 406 半回合；第 407 步检测到真实用户输入，系统按设计停止且没有重试。这个结果证明了安全门有效，但也诚实地留下了尚未完成的 1,000 半回合发布门槛。

## 第四阶段：把引擎分析提升为工作台

单个引擎能给出答案，多个引擎才能展示分歧。

PikaDesk 新增五引擎注册表和并行分析工作区：每个引擎拥有独立线程、Hash、MultiPV、启动超时和崩溃隔离；界面可以单独启停、隐藏和排序，并对同一局面计算共识与分歧。

官方 Pikafish 五进程实测覆盖了 PV1/PV2、暂停恢复、排序、停止门、零网络和进程清理。分析结果按局面代次隔离，旧局面的迟到输出不会污染新局面。

## 第五阶段：棋谱不再只是一条直线

项目建立了不可变节点值和稳定 UUID 组成的分支棋谱树，支持主线、变例、注释、评估、跳转、子树删除和整行原子合并。10,000 手压力测试验证了长棋谱的投影与路径恢复。

随后逐格式重建安全适配器：

- PGN：支持 ICCS 主线、变例、注释、结果和多种国内常见编码；
- XQF 1.0：严格按公开版本布局解析，高版本不猜测；
- CBR v2：用固定社区实现和两份真实样例交叉验证分支与 UTF-16LE；
- TXQ/PDTX：移除无限制 Java 对象反序列化，旧格式只走精确白名单迁移，新保存格式不执行对象代码。

所有格式都有输入大小、节点、深度、字符串和输出上限。无法无损表达的字段会明确警告或拒绝，不用“看似保存成功”掩盖数据损失。

## 第六阶段：时间、脚本与开局库

时间策略被实现为确定性纯函数：综合剩余时间、增益、预计步数、开中残局、比分和复杂度，为引擎给出可解释预算。50 组参数化测试覆盖临界值和极端输入。

智能脚本没有采用通用编程语言，而是设计成严格的 `PDSCRIPT 1` 白名单 DSL。脚本只能调用高层安全动作，拿不到窗口句柄、坐标、命令行或网络地址；授权走棋仍必须通过原安全状态机。

XQB v1 批量开局库工具支持多棋谱导入、去重、统计、进度、取消和跨进程恢复。PF/BH 的非公开变体仍在证据审计中，资料不足时项目选择明确拒绝，而不是猜测写入。

## 第七阶段：真实 Windows 验收与可携带镜像

项目在 Windows 11 上建立了两阶段 `jlink + jpackage` 流程，为 PikaDesk 生成自带 JRE 的开发镜像。打包脚本强制先跑完整测试，再收集运行依赖、资源、许可证提示和 SHA-256 清单。

工程迁入 `D:\象棋\PikaDesk` 后，Windows/GBK 环境暴露了 Surefire 模块路径损坏中文目录的问题。项目改用 Surefire 官方 classpath 模式并保留独立测试 JVM，最终在中文路径下实现 336/336 回归通过。

最新开发镜像包含 223 个文件、222 项哈希；启动响应正常，冒烟期间没有网络连接，测试结束后进程完整退出。

## 第八阶段：许可审计与公开协作

公开仓库保留完整上游归属、GPL v3、第三方依赖表、资源哈希、失败记录和功能对照矩阵。项目不会把尚未完成的能力包装成正式发布：

- YOLO 模型训练来源与字体许可仍是二进制发布阻断项；
- 1,000 半回合无人干预耐久测试尚未完成；
- 高对比主题、125%/200% DPI、语音和完整引擎联赛仍在路线图中；
- 公共平台排位实时辅助、自动走棋、反检测和授权绕过明确不在项目范围。

PikaDesk 选择把限制写在首页，把失败留在日志，把每一项“已经完成”建立在可重复执行的证据上。这种透明，正是开源项目最有价值的棋力。

## 第九阶段：建立真正独立的公开仓库

第一次公开时，GitHub 没有把 PikaDesk 标记为 Fork，但仓库仍保留了 99 个从 TCHESS 延续而来的提交。法律归属是清楚的，产品表达却不够清楚：读者看到的首先是一条上游开发线，而不是 PikaDesk 今天解决的问题、建立的工程契约和仍然承担的限制。

项目因此进行了第二次开源整理：

1. 用 Git bundle 完整备份原有提交、分支和上游引用，并验证 bundle 可恢复；
2. 按敏感文件名和常见密钥模式复审全部历史；
3. 参考成熟项目的信息层次重写首页，先说明问题、能力、实施链和证据，再说明来源；
4. 新增 `AGENTS.md`，把使命、安全边界、构建方法、文档规则和下一步优先级交给未来智能体；
5. 用 ADR 记录“独立根提交”和“保留 GPL 上游归属”为什么必须同时成立；
6. 在全量测试和链接检查通过后，以独立根提交重建公开 `main`。

公开仓库现在从 PikaDesk 自身开始讲述，但不会把独立身份包装成“全部代码从零开始”。TCHESS 固定基线、Pikafish 接入方式、GPL v3 义务、模型和字体阻断项仍然可以在 NOTICE 与第三方清单中逐项追溯。

## 我们如何判断一项工作已经完成

- 源码存在不等于能力可用：必须有定向测试或真实 E2E；
- 一次成功不等于稳定：必须覆盖失败、取消、超时、恢复和资源清理；
- 本机成功不等于可交付：必须固定工具链、记录哈希并在中文路径复验；
- 开源代码不等于资源可分发：模型、字体、权重和样例分别做来源与许可证审计；
- 功能相似不等于复制实现：以公开任务为目标，使用公开协议和本项目状态机独立落地；
- 宣传可以有立场，但不能越过证据。计划中的能力必须继续写成计划。

更细的逐项证据见[研究记录](../findings.md)、[进度日志](../progress.md)和[总任务计划](../task_plan.md)。
